description: 系统化盘问需求——产品级/系统级/功能级，产出到 oso/requirements/
---

对需求进行系统化盘问（interview），直到达成可执行的需求共识，产出写入 `oso/requirements/`。

**这是 OSO 的需求探索工具**——位于 OpenSpec 之前（意图层）。OpenSpec 管"怎么定义变更"，本工具管"要建什么系统、为什么"。

**Input**: 需求描述（自然语言）。可选参数指定级别/系统。

### 参数

```
/moya-interview                        # 默认：系统级盘问
/moya-interview --product              # 产品级盘问（绿地/转型/从0到1）
/moya-interview --system <名称>        # 系统级 + 指定系统（产品多系统时）
/moya-interview --feature <T>          # 功能级盘问 → 产出 backlog 条目（features.md）
/moya-interview --resume [级别]        # 回到指定级别继续（读已落盘文档）
/moya-interview --update [级别]        # 以指定级别为准，联动更新其他级别
/moya-interview --check                # 指出各级别对齐情况
```

### 产出位置

```
oso/requirements/
├── README.md              # 索引 + 对齐状态 + 迷雾
├── product.md             # 产品级（产品 = 哪些系统）
└── systems/
    ├── 01-<系统名>/
    │   ├── system.md      # 系统级（角色/边界/用例/契约/架构/风险）
    │   └── features.md    # 功能级（backlog 条目）
    └── ...
```

---

### Step 1: 参数解析

- `--product` → 产品级
- `--system <名称>` → 系统级 + 指定系统
- `--feature <T>` → 功能级（T 为功能标识，如 T1）
- `--resume [级别]` → 读 `oso/requirements/` 对应文件，从上次停下的地方继续
- `--update [级别]` → 见 Step 6
- `--check` → 见 Step 7
- 无参数 → 判断：`oso/requirements/` 已存在则提示 `--resume`；否则系统级

### Step 2: 盘问前检查（stance 保留）

**探索是思考对话，不是流程**——保留 OpenSpec explore 的姿态：好奇、不预设、可视化、落地。但本工具是**结构化盘问**（区别于自由探索的 `/opsx-explore`）：用户选择了被盘问，就按维度系统化提问。

先读代码/已有文档（事实自查）：

- 已有 `oso/requirements/` → 读相关文件（resume 场景）
- 已有代码库 → 读相关代码，能查到的不用问用户（事实自查，不问 obvious）
- 无代码库 → 直接从维度开始

### Step 3: 按维度盘问（轮次 + 推荐答案）

**机制**（借鉴 Matt Pocock grilling）：
- **设计树**：每个决策分叉出依赖它的子决策
- **按轮次（rounds）**：每轮问整个 frontier（前置已满足的问题），编号 + 附推荐答案
- **事实自查**：能查到的派子 agent 查，不问用户；查证中不阻塞
- **决策问人**：只有"选哪个"才问用户

**问题格式**：

```
❓ **Q1** - **<问题标题>**: <问题正文，可多段，含多个选项>

➡️ <推荐答案>
```

**完成标准**：
- **硬**：当前级别维度全部覆盖 + frontier 空（树走完、无沉默假设）
- **软**：能写出"没参与对话的人也能按它拆出工单"的需求共识
- **确认**：用户明确确认后才落盘

### Step 4: 按级别盘问（维度）

#### 产品级（--product / full）——问"产品组合"

| 维度 | 问什么 |
|---|---|
| **愿景与动机** | 这个产品要成为什么？解决什么根本问题？为什么是现在？ |
| **用户与市场** | 谁会用它？现在怎么解决（替代方案）？为什么选我们？ |
| **核心能力与差异化** | 哪几个能力是必须的（核心）？和替代方案比独特在哪？ |
| **成功指标** | 怎么衡量产品成功？（用户量/留存/收入…，不是"功能跑通"） |
| **系统构成** | 产品由哪几个系统/子系统组成？（每个系统一个目录） |

#### 系统级（默认）——问"单个系统的整体契约"

| 维度 | 问什么 |
|---|---|
| **角色** | 这个系统在更大的产品里扮演什么角色？负责什么转换？ |
| **边界** | 它管什么、**明确不管什么**？（哪些是别的系统的职责） |
| **用例** | 它对外提供哪些完整行为集合？（Use Case：参与者/前置/主流程/异常流/后置） |
| **外部契约** | 接口、依赖、数据流、与相邻系统的交互 |
| **架构与约束** | 技术栈？集成哪些系统？性能/安全/合规/扩展性？ |
| **风险与假设** | 最大的不确定性？哪些假设必须先验证（spike）？ |

#### 功能级（`--feature <T>`）——问"backlog 条目"

| 维度 | 问什么 |
|---|---|
| **WHO** | 给谁用？什么场景？ |
| **WHY** | 背景 + 目标 + 收益 |
| **WHAT** | 做什么 + 不做什么（范围边界） |
| **验收标准** | 可独立验证的条目（过/不过，不依赖主观判断） |

> 功能级产出 = **backlog 条目**（features.md），不是 sprint 任务。用户决定排期（计划会议）后，才由 `/moya-sprint` 引用/复制进 sprint。

### Step 5: 落盘（用户确认后）

盘问达成共识 → 展示摘要 → 用户确认 → 写入 `oso/requirements/`：

- 产品级 → `oso/requirements/product.md`
- 系统级 → `oso/requirements/systems/01-<系统名>/system.md`
- 功能级 → `oso/requirements/systems/01-<系统名>/features.md`
- README.md 同步更新（索引 + 对齐状态）

**文件名不加日期**（活文档，git 管版本）。落盘后建议下一步：
- 系统级确认后 → `/opsx-propose`（OpenSpec 细化）或 `/moya-interview --feature`（拆功能）
- 功能级确认后 → 用户决定排期 → `/moya-sprint`

### Step 6: --update（以指定级别为准，联动更新其他级别）

用户指定某级别为准 → 检查并更新其他级别的受影响内容：

- **产品级变更**（如系统构成变了）→ 影响 system.md（新增/删除系统目录）
- **系统级变更**（如边界变了）→ 影响 features.md（超出边界的功能移除）
- **功能级变更**（如验收标准变了）→ 通常不影响上游，只更新自身

**传播方向**：默认上游→下游单向（产品→系统→功能）。展示将变更的列表 → 用户确认 → 执行。

### Step 7: --check（指出各级别对齐情况）

比对 `oso/requirements/` 各文件，输出差异清单：

```
⚠️ 对齐检查结果：
- 系统级"用例：PR 触发评审" ↔ 功能级未覆盖（features.md 缺对应条目）
- 产品级"成功指标：月活1万" ↔ 系统级未映射到可验证标准
- ✅ 功能级 T2/T3 与系统级用例一致
- ❓ 迷雾：<还说不清的问题>
```

输出后询问用户是否修复（修复 = 进入对应级别盘问补缺）。

### Guardrails

- **不写代码**——interview 只盘问需求，不实现。实现是 `/opsx-apply` 的事
- **不跳过用户确认**——落盘/更新前必须用户确认（人不能自批）
- **事实自查，决策问人**——能查到的（代码/文档）自己查，只有决策才问用户
- **一次一个决策**（wayfinder 精神）——一个会话聚焦一个级别，不贪多；`--resume` 继续
- **不明就记迷雾**——说不清的记入 README 的"迷雾"区，不硬猜
- **功能级是 backlog 条目**——不直接安排 sprint；排期是 `/moya-sprint` 的事
- 已有 `oso/requirements/` 时建议 `--resume`，避免重复盘问
